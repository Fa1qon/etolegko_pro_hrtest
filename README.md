# netspeed

Консольный замер скорости скачивания: 10 последовательных запросов к адресу, каждый ответ читается до конца, в консоль выводится скорость.

## Запуск

Python 3.8+, только стандартная библиотека, ничего устанавливать не нужно.

```bash
python netspeed.py https://speedtest.selectel.ru/10MB
```
```
39.73 Mbit/s
```

## Единицы

**Mbit/s**: мегабиты в секунду, 1 Mbit = 10⁶ бит. В этих единицах провайдеры указывают тарифы, поэтому результат сравнивается с тарифом напрямую.

## Как считается

1. Адрес проверяется до первого запроса: только `http://` или `https://`, указан хост, порт число от 0 до 65535, нет пробелов и управляющих символов. Иначе выводится ошибка использования и код выхода `2`.
2. 10 запросов идут строго последовательно. Ответ читается до последнего байта блоками по 64 KB и не сохраняется, поэтому память не зависит от размера файла.
3. Неудачный запрос (HTTP 4xx/5xx, сервер молчит 10 с, обрыв соединения, ответ короче заявленного `Content-Length`) пишется в stderr и в расчёт не входит.
4. После 3 неудач подряд замер останавливается: адрес не работает, и оставшиеся попытки только заставили бы ждать. Если до этого были удачные запросы, скорость считается по ним.
5. По удачным запросам:
   - общий объём = сумма байт;
   - среднее время запроса = от отправки запроса до последнего байта ответа;
   - скорость = общий объём × 8 / (среднее время × число удачных запросов) / 10⁶.

Скорость считается как общий объём на общее время, а не как среднее из скоростей отдельных запросов. Среднее скоростей завышает результат: медленный запрос длится дольше, а в среднем весит столько же, сколько быстрый.

В stdout попадает только скорость, поэтому результат можно передать в другую программу без разбора. Коды выхода: `0` есть результат, `1` все запросы неудачны, `2` неверный адрес.

## Тесты

```bash
python -m unittest -v
```

Тесты поднимают локальный HTTP-сервер, интернет не нужен. Проверяется: ровно 10 запросов и одна строка в stdout, пропуск неудачных запросов, обрезанный ответ, остановка после 3 неудач подряд, отказ от невалидных адресов, формула скорости.

## Что бы улучшил

Скорее всего, скрипт — не самостоятельный инструмент, а источник данных для сервиса мониторинга. Следующий шаг — превратить его в компонент с явным контрактом:

- **Контракт данных.** Pydantic-модели для входа (`url: HttpUrl`, число запросов, таймаут) и для результата (замеры по каждому запросу, итоги, `schema_version`). Сгенерированная из них JSON Schema лежит в репозитории, тест падает при её расхождении с кодом. Вход строгий (`extra="forbid"`), выход читается терпимо: добавление поля не ломает потребителей.
- **Ошибки как часть ответа.** Результат с дискриминатором `status: ok | error` и типом ошибки (`timeout`, `http_status`, `network`). Потребитель сам решает, повторять ли запрос: таймаут стоит повторить, 404 — нет.
- **Разделение ядра и транспорта.** Функция `measure(request) -> report` без вывода и argv. CLI, HTTP-эндпоинт или воркер очереди — тонкие адаптеры над ней. HTTP-клиент подставляется через параметр, в тестах используется фейковый транспорт без сети.
- **Задержка отдельно от канала.** Хранить по каждому запросу время до первого байта: сейчас DNS, TCP и TLS входят в общее время и занижают скорость на маленьких файлах.
- **Режимы соединения.** Сравнивать «новое соединение на каждый запрос» и keep-alive: первое показывает то, что видит пользователь, второе — чистую пропускную способность.
- **Устойчивость.** Предел времени на весь запрос (сейчас таймаут срабатывает только на тишину), предел размера ответа, ожидание по `Retry-After` при ответе 429. DNS-запрос стандартная библиотека не ограничивает таймаутом, на несуществующем домене его время задаёт системный резолвер (на Windows около 11 с на попытку).
- **Точность на быстрых каналах.** Один TCP-поток не всегда заполняет канал от 1 Gbit/s, нужен режим с несколькими параллельными потоками.
